Academic Concepts & Educational Explanations
College PBL Theory Guide

1. Network Congestion in Banking

Network congestion occurs when the volume of incoming transaction requests exceeds the processing capacity of the web servers or database connection pools. During festive sales, salary days, or stock market opens, millions of concurrent users hit banking APIs simultaneously.

2. Rate Limiting & Admission Control

Rate limiting restricts how many requests are accepted per second. Instead of allowing servers to crash under memory exhaustion, admission control admits manageable traffic (e.g. 20 req/s) and rejects or deflects excess queries with polite HTTP 429 status codes.

3. Priority Request Queuing

A buffer absorbs momentary traffic spikes. Rather than strict FIFO, banking systems use Priority Queuing: financial transfers and card authorizations receive Priority 1, while background balance inquiries receive Priority 2 or 3.

4. Latency vs. Throughput

Latency is the total time (queue wait + processing) taken to return a response to the client. Throughput is the number of requests successfully processed per second. Congestion control prevents throughput collapse and bounds maximum latency.

5. Request Loss & Timeout/Retry

When servers are overwhelmed without congestion control, requests hang indefinitely until client sockets timeout (30+ seconds), triggering aggressive client retries that further compound the crash (the classic "retry storm" problem).

6. Application-Level vs. TCP Packet-Level

Crucial distinction for viva: TCP congestion control (e.g. Reno, Cubic, BBR) operates in the OS kernel at Layer 4, adjusting window sizes for byte packets. NexaBank implements Application-Level Congestion Control (Layer 7), inspecting HTTP transactions, managing worker capacity, and prioritizing high-value banking operations.
